## Candidate findings

Each survived the debate against it: the quoted sentence is in the file, the charitable reading was tried, and two implementers would diverge.

### F1. The slicing-matrix entry cannot encode a multi-layer bundle, so the M = 2 rung is undefined on the wire (High)

With the reference ladder (L = 3) and M = 2, Ch1 §1.2.4 §4.2.1 puts "bundles {L0+L1}, {L2}" on Trees 1 and 2. App D §D.4.8 and Ch2 §2.3.3 encode the matrix as `[TreeID 1B][Layer 1B][StripeIndex 1B][StripeCount 1B][Priority 1B][BitrateKbps 2B] × NumTrees`: one `Layer` per tree. The entries are (T1, Layer 0, 3000) and (T2, Layer 2, 3000); L1 is in no entry. §D.4.8 says block j′ of layer l "travels on the tree of layer l", so the 3 layer-1 blocks of every chunk (j = 3..5) have no tree. The Stream Record carries no LayerCount, so a joiner reading it cannot even bound the top tree's bundle. Ch1 §1.2.4 §1.4 says "Peers never derive the layer mapping … never inferred", which rules out the only workaround. The implementation does infer: `SlicingMatrix::from_entries` (src/crates/bs-media/src/mapping.rs, lines 176 to 199) fills `layer_end` from the gap to the next entry's `layer`, using a `layer_count` that the Stream Record does not carry. A second implementer who emits one entry per (tree, layer) pair makes NumTrees = 3 ≠ M, which breaks rendezvous assignment over M. Fix: give the entry a `LayerEnd` (or `LayerCount`) byte and add `LayerCount` to the Stream Record; blast radius App D §D.4.8, Ch2 §2.3.3, Ch1 §1.2.4, the proto schema.

### F2. The first PING must carry a dynamic puzzle bound to an address the node learns only from the PONG (Medium)

Ch2 §2.2.3: "Every pre-session plain-UDP frame (PING/PONG, …) must carry the cryptographic ID validation block", and the verifier "checks the dynamic Proof-of-Work against the observed UDP source address". Ch2 §2.1.3 step 2 makes the PONG reflection the source of that address ("A node that solves the dynamic puzzle against a reflected address already has both reflections in hand"), and App D §D.4.1 says the reflection replaces STUN. A `PUBLIC` node can guess its local address, which is why this walk passes; a node behind any NAT cannot, so its first PING fails verification and under §2.2.3 the seed sends no PONG. The node then never learns its reachability class and never advances past BOOTSTRAP. Ch6 §6.2.1 lists `QuerySTUNServers` as a step, but the bootstrap sequence of Ch2 §2.1.3 does not invoke it and §D.4.1 says it is unnecessary. The implementation takes the strict reading: `on_ping` (src/crates/bs-core/src/node.rs line 2029) verifies the dynamic puzzle against `from.ip()`, and the sender solves against its configured local address (line 445). Fix: state that a seed verifies the static puzzle only on PING and answers PONG regardless of the dynamic one (the 65,536-hash static puzzle still rate-limits), or require a STUN step before the first PING.

### F3. At N = 2 the only backfill provider is the source, which has no PULL budget and no unchoke slot (Medium; cluster with ISSUE-066)

Ch4 §4.3.1 step 5: "PULL any blocks of segment X (and any gaps) from active-set neighbors to fill the initial buffer." At N = 2 the viewer's only neighbour is the source. Ch1 §1.1.5 §5.4: "the source serves no PULL_REQUESTs from the live edge, so no r_pull share is withheld", so PullSlots_S = 0, and Ch5 §5.1.3: "If PullSlots <= 1 then SlotCount <- 0 // cannot afford exploration", so the viewer is never unchoked. Under that reading the viewer's first decodable GOP is the first one pushed complete, segment 12 at 11,615, which renders at 14,490 under the 3.0 s rule: SJL 4.49 s, with a 0 s buffer if rendered earlier. Under the charitable reading (the source serves backfill from headroom) the numbers are: backfill of 3 s × 6 Mbps = 18 Mb; headroom 20 − 6.92 − 5.19 = 7.9 Mbps → 2.3 s to fill a 3 s buffer, SJL 0.93 s; with the two viewers K_S allows joining together, 36 Mb at 7.9 Mbps = 4.6 s > 3 s, so the second viewer's buffer underruns during fill-in. ISSUE-066 records the repair half of this (the cooldown denies repair in "the two-node case"); the backfill half and the missing source budget are not in it. The implementation serves pulls at the source (`pull_allowed`, src/crates/bs-core/src/node/incentive.rs line 919, serves a child's pulls for a tree it pushes) with no budget. Fix: define the source's PULL role (backfill of retained segments and repair of its own stripes) and charge it to a named share of u_S − R_src; state the resulting bound on simultaneous joiners.

### F4. The startup render rule is undefined: strict chunk deadlines cost 0.8 s of SJL at N = 2 (Low)

Ch4 §4.3.1: "The playout deadline sits Δ_buffer = 3.0 s behind the received live edge", and rule 2 allows a position "more than one segment beyond the 3.0 s target" to be corrected forward, which implies up to one segment behind is tolerated. Nothing says whether the first frame may render behind the target. At tick 10,930 the anchor (11, 1) at 10,740 puts deadline(8, 0) at 10,490, already past, so an implementer who applies the scheduler's "Too late to decode" rule starts at segment 9 at 11,740 (SJL 1,740 ms, over the 1.5 s target of Ch8 §8.2); one who starts on the first complete GOP renders at 10,930 (SJL 930 ms) and runs 440 ms behind target. Fix: one sentence in Ch4 §4.3.1, "playback starts at the oldest complete GOP whose deadline is no more than one segment past", and SOLUTION-033's SJL validation should name it. The implementation anchors at the newest manifest and sets backfilled chunks' deadlines at negative offsets from anchor + 3.0 s (src/crates/bs-core/src/swarm.rs lines 232 to 245), the strict reading.

### F5. Segment numbering after a source restart is unspecified; a reset strands every surviving viewer (Medium; sibling of ISSUE-070)

No sentence in `protocol/` says what SegmentSeq a restarted source emits. Ch7 §7.1.2 admits a manifest only if `X_edge − 8 <= seq <= X_edge + 2`, and Ch4 §4.3.1 rule 3: "Never re-anchor backward. X_edge is monotonically non-decreasing." Neither Ch1 §1.3.1 nor §1.3.2 resets X_edge on the fall to DISCOVERY. At tick 65,700 the viewer holds X_edge = 60, window [52, 62]. A source that restarts at seq 1 is rejected forever: the viewer is evicted for unreceipted segments at ≈ 68,700, rejoins, and repeats. Any guardian that still holds the old record rejects the restarted source's STORE_RECORD for up to 180 s, because Ch2 §2.3.3 accepts only when ManifestVersion and LiveEdgeSegmentId are "not lower than the record it holds" and both restart from 1 (the implementation's `record_version` starts at 0). A source that continues its counter (seq 61) works only because the gap stayed inside LOOKAHEAD = 2; a wall-clock-derived 66 is ISSUE-070. Fix: require the source to persist SegmentSeq and ManifestVersion across restarts (or derive both from a monotonic stream clock), and have a peer that leaves ACTIVE with no parent clear X_edge so CONNECTING re-anchors from the Stream Record; blast radius Ch2 §2.3.3, Ch4 §4.3.1, Ch7 §7.1.2, Ch1 §1.3.1.

### F6. The implementation computes the source's slots with the relay formula, not with R_src (Low, impl)

Ch1 §1.1.5 §5.4: `K_S(m) = ⌊(u_S − R_src) / (M · B_m · Ω)⌋`, with no r_pull. `recompute_slots` (src/crates/bs-core/src/node.rs lines 500 to 524) calls `Params::slots` for the source too, which uses `(1 − r_pull − slot_headroom) · u_S` = 0.85 u_S and holds back no base-layer reserve. At 20 Mbps both give 2 slots per tree; at 40 Mbps the spec gives ⌊34.81 / 6.917⌋ = 5 and the implementation ⌊34 / 6.917⌋ = 4; at 100 Mbps, 13 against 12. The emergency pool of §5.4 is never held in the implementation.
