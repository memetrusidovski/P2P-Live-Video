# 2. Progressive Blake3 Hashing

A primary vector of P2P disruption is block poisoning, where a malicious node injects corrupted bytes to stall downstream decoders. To neutralize this without introducing verification latency, each 250 ms **chunk** of the segment (§1) is divided into $16\text{ KB}$ blocks and structured as a **Blake3 Merkle Tree**:

```text
                                [ Signed Manifest Root ]  (Ed25519 Signed by Source)
                                      /          \
                                 [Hash L]      [Hash R]
                                  /    \        /    \
                               H(0)   H(1)    H(2)   H(3)
                                |      |       |      |
                              [B_0]  [B_1]   [B_2]  [B_3] <-- 16KB Data Blocks
```

Let a chunk be divided into $N$ blocks: $\mathcal{B} = \{B_0, B_1, \dots, B_{N-1}\}$ (at $6$ Mbps, $N \approx 12$; the tree is 4 levels deep). The Merkle Tree is constructed as follows:
1.  **Leaf Hashing:** Every block $B_i$ is hashed using the ultra-fast Blake3 hash:
    $$h_i = \text{Blake3}(B_i)$$
2.  **Internal Node Hashing:** Parent nodes are generated by hashing the concatenation of their children:
    $$h_{x,y} = \text{Blake3}(h_x \parallel h_y)$$
3.  **Root Generation:** The process repeats until a single 32-byte Root Hash $H_{\text{root}}$ is obtained.
4.  **Manifest Signature:** The broadcaster signs the Root Hash along with the segment sequence number and chunk index — the full `MANIFEST` payload of Appendix D §D.4.8:
    $$\text{Sig}_{\text{Manifest}} = \text{Sign}_{SK_{\text{Source}}}(\text{StreamID} \parallel \text{SegmentSeq} \parallel \text{ChunkIndex} \parallel \ldots \parallel H_{\text{root}} \parallel \ldots)$$

When a client downloads a single block $B_i$, the sender bundles it with the **Merkle Path Proof** (the set of sister hashes needed to reconstruct the path to the root). For example, to verify $B_0$, the client receives $B_0$ and the sister hashes $\{h_1, h_{2,3}\}$.

The client executes the progressive verification:
$$h_0' = \text{Blake3}(B_0)$$
$$h_{0,1}' = \text{Blake3}(h_0' \parallel h_1)$$
$$H_{\text{root}}' = \text{Blake3}(h_{0,1}' \parallel h_{2,3})$$

If $H_{\text{root}}' == H_{\text{root}}$ (extracted from the signed manifest), **the client validates the block and immediately forwards it to downstream children**, achieving sub-millisecond, zero-trust progressive verification.

## Blocks vs. Symbols: The Verification Boundary

The 16 KB Merkle block and the 1024 B RaptorQ symbol (Ch4 §4.2) are two views of the same data unit: **one RaptorQ source block per Merkle block**, encoded as $K = 16$ source symbols plus adaptive parity. The `SBN` field of every `RAPTORQ_SYMBOL` frame is the Merkle block index.

The zero-trust verification boundary is the **block**, never the symbol:

*   Symbols are a link-local loss-recovery encoding. They carry no Merkle proofs (per-symbol proofs would add ~19% overhead to a 1 KB payload) and are **never individually verified or forwarded raw**.
*   An interior relay operates **decode → verify → re-encode → push**: reconstruct block $B_i$ from any $\ge 16$ received symbols, verify it against the signed manifest root using its Merkle path (delivered via the `BLOCK_PROOF` 0x13 frame on the push path, or inline in `BLOCK_TRANSMISSION` 0x10 on the pull path), and only then generate *fresh* symbols — with parity sized per downstream link (§4.2.2) — for its children.
*   A block that fails verification is dropped, the delivering parent is flagged (Ch5 §5.3), and the block is re-pulled from an alternate neighbor.

This preserves the verify-then-forward guarantee end-to-end: corrupted data can never propagate further than one hop, while loss recovery still operates at fine symbol granularity on each link. Proof-of-Upload receipts (Ch5 §5.2) attest verified blocks — one receipt per segment per tree carrying a bitmap of the blocks verified.

### The Per-Hop Cost of Block-Boundary Verification

Choosing the block as the verification boundary makes every interior relay **store-and-forward at 16 KB granularity**: it cannot emit a symbol of block $B_i$ until it holds and has verified all of $B_i$. That is a real per-hop cost and belongs in the latency budget of §1.1.2 explicitly rather than being assumed away. It is small, and the reason it is small is worth stating because a naive implementation will make it large:

| Step | Cost per block per hop |
| :--- | :--- |
| Accumulate $\ge K = 16$ symbols | $\approx \text{16 KB} / u_{\text{link}}$ — 13 ms at 10 Mbps. **Dominant term.** |
| RaptorQ decode | **Zero in the common case** — see below |
| Blake3 hash of 16 KB + Merkle path ($\le 4$ sister hashes per chunk tree) | $\sim 5\ \mu\text{s}$ |
| Re-encode $E$ parity symbols | $\sim$ microseconds |

**Decoding is a no-op when nothing was lost.** RaptorQ is a *systematic* code: source symbols $\text{ESI} < K$ are the block's raw 1 KB slices, unmodified. If all 16 source symbols arrive — the overwhelmingly common case, which is why parity is sized at only 5–30% — the relay reconstructs the block by **concatenating them**, with no decoding work at all. The RaptorQ decoder is invoked only when a source symbol is missing and must be recovered from parity.

An implementation that runs a full decode pass on every block at every hop therefore pays a cost the design does not require, and at a million-peer scale that is the difference between a negligible per-hop term and a dominant one.

### Repair Symbols Must Not Collide Across Responders

Because every relay decodes to the *identical* verified block, and RaptorQ symbol generation is deterministic in $(\text{block}, \text{ESI})$, symbols produced by different relays for the same block are interchangeable — a child may combine symbols from several parents freely. That is a useful property, but it creates a duplication hazard: a child repairing block $B_i$ from two neighbours receives *the same* repair symbols from both if each responder simply generates $\text{ESI} = K, K{+}1, \dots$

`PULL_REQUEST` (0x16) carries a `MissingSymbolCount` but no indication of which symbols the requester already holds, and widening it would need the requester to enumerate them. The fountain-code property makes that unnecessary — *any* $K$ distinct symbols decode the block — so responders simply choose disjoint ranges instead:

$$\text{ESI}_{\text{base}}(v) = K + \left(\text{Blake3}(NodeID_v)\ \bmod\ (2^{16} - K - 256)\right)$$

Each responder emits its repair symbols from its own derived base. Two responders collide only on a birthday coincidence in a ~65,000-wide space, so a child pulling from several neighbours accumulates *distinct* symbols and reaches $K$ in the minimum number of packets. Source symbols ($\text{ESI} < K$) are unaffected — those are the raw slices and are identical everywhere by definition.
